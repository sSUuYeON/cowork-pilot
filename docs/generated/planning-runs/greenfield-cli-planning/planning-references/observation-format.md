# Brownfield 코드 관찰 형식 레퍼런스

이 문서는 brownfield 코드 관찰 단계에서 사용하는 기록 형식, 종합 문서 구조, 금지 표현, 태그 규약을 정의한다.

---

## §1 관찰 항목별 기록 형식

각 관찰 카테고리는 아래 형식을 정확히 따라야 한다. 형식을 임의로 변경하지 마라.

### 프레임워크 및 라이브러리

```
- {이름}@{버전} — {용도} (근거: {파일경로})
```

예시:
```
- fastapi@0.104.1 — HTTP 라우팅 및 API 서버 (근거: pyproject.toml:15)
- sqlalchemy@2.0.23 — ORM 및 DB 접근 (근거: requirements.txt:3)
```

버전 번호는 반드시 lock 파일(package-lock.json, poetry.lock, Cargo.lock) 또는 manifest 파일(package.json, pyproject.toml, Cargo.toml)에서 확인된 값만 기록한다. 확인할 수 없으면 `@unknown`으로 표기하고 `[UNVERIFIED]` 태그를 단다.

### 아키텍처 패턴

```
- 패턴: {패턴명}
  근거 파일: {파일경로}
  판단 근거: {이 패턴으로 판단한 구체적 이유}
```

예시:
```
- 패턴: Layered Architecture (Controller → Service → Repository)
  근거 파일: src/api/routes.py, src/services/user_service.py, src/repositories/user_repo.py
  판단 근거: routes.py가 service를 호출하고, service가 repository를 호출하는 단방향 의존 체인이 존재
```

단순히 "MVC", "Hexagonal" 등 패턴명만 적지 마라. 왜 그 패턴인지 근거를 반드시 서술하라.

### 데이터 모델

```
- 모델: {모델명}
  필드 수: {N}개
  주요 관계: {관계 설명}
  근거 파일: {파일경로:라인}
```

예시:
```
- 모델: User
  필드 수: 12개
  주요 관계: User 1--N Order, User 1--1 Profile
  근거 파일: src/models/user.py:15-42
```

### API 엔드포인트

```
| METHOD | 경로 | 핸들러 | 인증 필요 |
|--------|------|--------|-----------|
| {METHOD} | {/path} | {파일:라인} | {Y/N} |
```

예시:
```
| METHOD | 경로 | 핸들러 | 인증 필요 |
|--------|------|--------|-----------|
| GET | /api/users | src/api/users.py:23 | Y |
| POST | /api/users | src/api/users.py:45 | N |
```

### 테스트 구조

```
- 테스트 프레임워크: {이름} (근거: {설정파일경로})
- 테스트 파일 수: {N}개
- 테스트 디렉토리: {경로}
- 커버리지 설정: {있음/없음} (근거: {파일경로})
- CI 연동: {있음/없음} (근거: {파일경로})
```

### 설정 및 환경

```
- 설정 파일: {파일명} — {용도} (근거: {파일경로})
- 환경 변수: {변수명} — {용도} (사용처: {파일경로:라인})
```

환경 변수의 실제 값은 기록하지 마라. 변수명과 용도만 기록한다.

### 코드 원문 추출 규칙

관찰의 근거가 되는 코드는 **요약하지 말고 원문을 그대로 복사**한다. 복사한 코드 블록 앞에 반드시 SOURCE 주석을 단다:

```
<!-- SOURCE: {파일경로}:{시작라인}-{끝라인} -->
```

예시:
```markdown
<!-- SOURCE: src/api/routes.py:15-23 -->
```python
@app.get("/users/{user_id}")
async def get_user(user_id: int, db: Session = Depends(get_db)):
    return db.query(User).filter(User.id == user_id).first()
```
```

규칙:
- 한 코드 블록이 여러 관찰 항목에 관련되면 양쪽 다 복사하라 (중복 허용)
- 관련 없는 코드만 제거하고, 나머지는 원문 그대로 유지하라
- 코드를 "정리"하거나 "간략화"하지 마라
- SOURCE 주석이 없는 코드 블록은 유효하지 않다

## §2 슬라이스 파일 구조

각 슬라이스 파일은 아래 마크다운 구조를 따른다:

```markdown
# 코드 관찰: {슬라이스명}

## 탐색 범위

- 루트 디렉토리: {경로}
- 탐색 depth: {N}
- 파일 수: {N}개

## {모듈명 1}

### 프레임워크 및 라이브러리
(§1 형식에 따라 기록)

### 아키텍처 패턴
(§1 형식에 따라 기록)

### 데이터 모델
(§1 형식에 따라 기록)

### API 엔드포인트
(§1 형식에 따라 기록)

### 테스트 구조
(§1 형식에 따라 기록)

### 설정 및 환경
(§1 형식에 따라 기록)

## {모듈명 2}
(동일 구조 반복)
```

슬라이스 하나의 권장 크기: 모듈 3~5개. 프로젝트가 작으면 슬라이스 1개로 충분하다.

해당 모듈에 특정 카테고리가 없으면 `(해당 없음)` 으로 표기한다. 카테고리 헤더 자체를 생략하지 마라.

## §3 종합 문서 구조

`implementation-observation-summary.md`는 아래 구조를 따른다:

```markdown
# 코드 관찰 종합

## 참조 슬라이스
- {슬라이스1 파일명}
- {슬라이스2 파일명}
- ...

## 아키텍처 개요

레이어 구조를 서술한다. 진입점에서 시작하여 핵심 처리 흐름, 데이터 저장까지 순서대로 기술한다.

형식:
진입점({파일}) → 라우팅({파일}) → 비즈니스 로직({파일}) → 데이터 접근({파일}) → 저장소({종류})

## 데이터 모델 요약

엔티티 간 관계를 아래 형식으로 기록한다:
{엔티티A} --[{관계}]--> {엔티티B}

예시:
User --[1:N]--> Order
Order --[N:1]--> Product
Product --[N:N]--> Category

## API 표면 요약

| 그룹 | METHOD | 경로 | 핸들러 | 인증 |
|------|--------|------|--------|------|
| {기능 그룹} | {METHOD} | {/path} | {파일:라인} | {Y/N} |

## 주요 의존성 목록

| 이름 | 버전 | 용도 | 직접/간접 |
|------|------|------|-----------|
| {패키지명} | {버전} | {용도} | {직접/간접} |

직접 의존성: manifest 파일에 명시된 것
간접 의존성: lock 파일에만 존재하는 것

## 코드 패턴 및 컨벤션

| 패턴 | 사용처 수 | 예시 파일 |
|------|-----------|-----------|
| {패턴명} | {N}곳 | {파일경로} |

## 모순 사항

(모순이 없으면 "발견된 모순 없음"으로 기록)

형식:
- [CONFLICT] {관찰 내용}
  슬라이스 A: {파일명} — {내용}
  슬라이스 B: {파일명} — {내용}
```

## §4 금지 표현

아래 표현은 관찰 기록 및 종합 문서에서 사용을 금지한다:

- "~인 것 같다", "~로 보인다", "아마", "추정컨대"
- "전반적으로", "대체로", "일반적으로"
- "적절한", "필요시", "충분한"
- "등등", "기타", "및 기타"
- "TBD", "TODO", "추후 작성", "나중에 확인"

확인할 수 없는 사항은 추측 표현 대신 `[UNVERIFIED]` 태그를 사용하라.

## §5 태그 규약

| 태그 | 의미 | 사용 조건 |
|------|------|-----------|
| `[UNVERIFIED]` | 소스 코드에서 직접 확인하지 못한 관찰 | lock 파일/manifest에서 버전을 확인할 수 없을 때, import만 보고 실제 사용을 확인하지 못했을 때 |
| `[CONFLICT]` | 슬라이스 간 모순되는 관찰 | 동일 모듈/기능에 대해 두 슬라이스가 서로 다른 내용을 기록했을 때 |
| `[UNCERTAIN]` | 관찰 자체가 불확실한 경우 | 코드가 난독화되어 있거나, 동적 로딩으로 정적 분석이 불가할 때 |

태그는 해당 항목의 첫 줄 끝에 붙인다:

```
- fastapi@unknown — HTTP 서버 (근거: pyproject.toml:15) [UNVERIFIED]
```
