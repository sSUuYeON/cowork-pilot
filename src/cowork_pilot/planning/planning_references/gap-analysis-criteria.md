# Brownfield 갭 분석 기준 레퍼런스

이 문서는 brownfield 갭 분석 단계에서 사용하는 갭 항목 기록 형식, 변경 난이도 기준, 갭 분류, 의존성 표기, 검증 규칙을 정의한다.

---

## §1 갭 항목 기록 형식

각 갭 항목은 아래 형식을 정확히 따라야 한다.

```markdown
### GAP-{NNN}: {한 줄 요약}

- **분류**: {spec-implementation-gap | change-impact-gap}
- **설명**: {갭의 구체적 내용. 현재 상태와 기대 상태의 차이를 명시}
- **영향 파일**:
  - {파일경로1}
  - {파일경로2}
- **변경 난이도**: {low | medium | high} (§2 기준 적용)
- **난이도 근거**: {§2의 어떤 기준에 해당하는지 구체적으로 명시}
- **의존성**: {→ GAP-NNN | 없음}
```

예시:

```markdown
### GAP-001: User 모델에 email_verified 필드 누락

- **분류**: spec-implementation-gap
- **설명**: 스펙은 이메일 인증 플로우를 요구하지만 현재 User 모델에 email_verified 필드가 없다
- **영향 파일**:
  - src/models/user.py
  - src/api/auth.py
- **변경 난이도**: medium
- **난이도 근거**: 2개 파일 수정 + 마이그레이션 필요 (§2 medium 기준 해당)
- **의존성**: 없음
```

GAP-ID는 `GAP-001`부터 순차 증가한다. 번호를 건너뛰지 마라.

## §2 변경 난이도 기준

난이도는 아래 기준으로 **기계적으로** 판단한다. "느낌"이나 "경험적 판단"으로 결정하지 마라.

### low

아래 조건을 **모두** 만족해야 한다:

- 수정 대상 파일이 **1개**
- 기존 코드 패턴 내에서 변경 가능 (새 패턴 도입 불필요)
- 기존 테스트에 영향 없음 (테스트 수정 불필요)
- 데이터 모델 변경 없음
- 설정/환경 변수 변경 없음

예시: 기존 API 엔드포인트에 쿼리 파라미터 1개 추가, 유틸 함수 내부 로직 수정

### medium

아래 조건 중 **하나 이상** 해당:

- 수정 대상 파일이 **2~5개**
- 새 함수, 클래스, 또는 모듈 추가 필요
- 기존 테스트 수정 필요 (테스트 케이스 변경 또는 추가)
- 단순 필드 추가 수준의 데이터 모델 변경 (마이그레이션 필요하지만 관계 변경 없음)
- 새 환경 변수 추가

예시: 새 API 엔드포인트 추가, 기존 모델에 필드 추가 + 마이그레이션, 새 서비스 클래스 생성

### high

아래 조건 중 **하나 이상** 해당:

- 수정 대상 파일이 **6개 이상**
- 아키텍처 패턴 변경 (예: 동기 → 비동기, 모놀리스 → 마이크로서비스)
- 데이터 모델 관계 변경 (1:N → N:N, 엔티티 분리/병합)
- 데이터 마이그레이션이 기존 데이터에 영향 (기본값으로 해결 불가)
- 외부 서비스/라이브러리 교체
- 인증/권한 체계 변경

예시: ORM 교체, 인증 시스템 전면 교체, 데이터베이스 스키마 대규모 변경, 모듈 간 의존성 방향 변경

### 판단 순서

1. high 조건에 하나라도 해당하면 → **high**
2. medium 조건에 하나라도 해당하면 → **medium**
3. low 조건을 모두 만족하면 → **low**
4. 판단이 불가능하면 → **medium** + `[UNCERTAIN]` 태그

## §3 갭 분류

갭은 두 종류로 분류한다. 하나의 갭이 두 분류에 동시에 해당할 수 없다.

### spec-implementation-gap

**정의**: 스펙/기획서가 요구하지만 현재 코드에 구현되어 있지 않은 것

판단 기준:
- 스펙 문서에 명시된 기능/동작이 코드에 없다
- 스펙이 요구하는 데이터 필드가 모델에 없다
- 스펙이 정의한 API가 구현되어 있지 않다

입력: implementation-observation-summary.md (현재 상태) + 기획서/스펙 문서 (기대 상태)

### change-impact-gap

**정의**: 변경 요청을 적용할 때 기존 코드에서 수정이 필요한 부분

판단 기준:
- 변경 요청이 기존 함수/클래스의 시그니처 변경을 요구한다
- 변경 요청이 기존 데이터 모델의 수정을 요구한다
- 변경 요청이 기존 테스트의 수정을 요구한다
- 변경 요청이 기존 설정/환경의 변경을 요구한다

입력: implementation-observation-summary.md (현재 상태) + normalized-request.md / change-request.md (변경 요청)

### 분류 기록 형식

갭 문서는 분류별로 섹션을 나눈다:

```markdown
# 갭 분석 결과

## spec-implementation-gap

### GAP-001: ...
### GAP-002: ...

## change-impact-gap

### GAP-003: ...
### GAP-004: ...

## 요약

| 분류 | 갭 수 | low | medium | high |
|------|-------|-----|--------|------|
| spec-implementation-gap | {N} | {N} | {N} | {N} |
| change-impact-gap | {N} | {N} | {N} | {N} |
| 합계 | {N} | {N} | {N} | {N} |
```

## §4 의존성 표기

갭 간 의존성은 `→ GAP-NNN` 형식으로 표기한다.

```
- **의존성**: → GAP-003, → GAP-007
```

의미: 이 갭을 해결하려면 GAP-003과 GAP-007이 먼저 해결되어야 한다.

### 순환 의존성

갭 A → 갭 B → 갭 A 같은 순환이 발견되면:
1. 해당 갭들에 `[CIRCULAR]` 태그를 단다
2. 순환 경로를 명시한다: `[CIRCULAR] GAP-003 → GAP-007 → GAP-003`
3. 해결 방법은 제시하지 마라 — 순환 존재만 기록한다

### 의존성 없음

의존성이 없으면 반드시 `없음`으로 표기한다. 필드를 생략하지 마라.

## §5 검증 규칙

갭 분석 완료 후 아래 규칙으로 자체 검증한다.

### 필수 검증 항목

1. **영향 파일 존재**: 모든 갭에 영향 파일이 1개 이상 있는가?
   - 위반 시: 영향 파일을 찾을 수 없으면 `[UNCERTAIN]` 태그를 달고 사유를 기록
   - 영향 파일 없이 확실한 갭은 존재할 수 없다

2. **난이도 근거 명시**: 모든 갭에 §2 기준에 근거한 난이도 판단이 있는가?
   - 위반 시: "§2 기준 적용" 부분을 다시 작성

3. **GAP-ID 연속성**: GAP-001부터 빈 번호 없이 연속인가?
   - 위반 시: 번호를 재정렬

4. **분류 정확성**: 각 갭이 §3의 판단 기준에 맞는 분류에 있는가?
   - spec-implementation-gap에 변경 요청 기반 갭이 섞이지 않았는가?
   - change-impact-gap에 스펙 누락 갭이 섞이지 않았는가?

5. **요약 테이블 정합성**: 요약 테이블의 숫자가 실제 갭 항목 수와 일치하는가?
   - 위반 시: 테이블을 재계산

### 금지 사항

- 갭의 해결 방법, 리팩토링 방안, 구현 제안을 작성하지 마라
- scope, work item, plan chunk를 생성하지 마라
- 갭이 아닌 개선 제안을 갭으로 기록하지 마라 (현재 동작하는 기능의 "더 나은 구현"은 갭이 아니다)

### 금지 표현

- "~하면 좋겠다", "~할 수도 있다", "~를 고려해볼 만하다"
- "적절한", "필요시", "충분한"
- "등등", "기타", "및 기타"
- "TBD", "TODO", "추후 작성", "나중에 확인"
